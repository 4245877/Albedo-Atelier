## Как проверять

```bash
# orchestrator (изолированно от реальной фермы: пустой конфиг принтеров, временное состояние)
cd apps/print-orchestrator
node_modules/.bin/tsc -p tsconfig.json --noEmit
TZ=UTC PRINTERS_CONFIG_PATH=/tmp/x/no-printers.json PRINTERS_CONFIG_JSON='[]' \
  STATE_FILE_PATH=/tmp/x/state.json ORCA_SLICER_CMD= \
  node --experimental-sqlite --disable-warning=ExperimentalWarning --import tsx --test "src/**/*.test.ts"

# dashboard
cd apps/print-dashboard && node --test "tests/**/*.test.mjs"
```

Без `PRINTERS_CONFIG_PATH` значение по умолчанию — `config/printers.json`, то
есть **реальная ферма**. Тесты, собирающие рантайм, обязаны получать пустой
конфиг.

Уточнения по изоляции (выяснены на этапе 2):
- Каталог для `STATE_FILE_PATH` лучше брать **свежий на каждый прогон**
  (`mktemp -d`) и удалять после: `queue.db` и хранилище артефактов по умолчанию
  выводятся из него, и остатки прошлого прогона попадают в синглтон-тесты.
- **Не задавать** `QUEUE_DB_PATH` / `ARTIFACT_STORAGE_ROOT` снаружи: тесты
  маршрутов изолируют себя собственным `STATE_FILE_PATH`, а внешний
  `QUEUE_DB_PATH` перебивает это и сводит все синглтон-тесты в одну БД (ложное
  падение «slicing endpoints never expose the legacy queue»).
- **Не править исходники во время прогона**: worker анализа загружает `.ts` с
  диска при каждом запуске, и правка посреди прогона даёт ложные падения в
  тестах, которые идут позже.

### CRITICAL-01 — отмена во время запуска
- `TaskCommands.cancel()` различает четыре случая: ожидающая работа
  (логическая отмена); старт «в полёте» (записывается намерение отмены на run,
  стол и задание не трогаются); идущая печать (отказ, только физическая
  остановка); несогласованный хвост (стол → `UNKNOWN`, не `CLEAR`).
- Намерение отмены проверяется **внутри блокировки принтера непосредственно
  перед записью guard и отправкой** (`StartPrintOptions.beforeSend`). Если
  команда не ушла — запуск прерывается, задание закрывается, стол возвращается.
  Если ушла — принтер удержан до телеметрии/решения человека; после «печать не
  началась» задание закрывается, а не возвращается в очередь.
- `PrintQueueContext.unwindAssignment` больше никогда не отменяет run логически
  и не освобождает стол при живом run.
- Замена плана (`cancelActive`) больше не отменяет `RESERVED/ACTIVE` назначения.
- Новый маршрут `POST /api/print/tasks/:id/stop` — физическая остановка печати
  задания с проверкой идентичности (run + файл). `POST /tasks/:id/cancel`
  возвращает `outcome: cancelled | cancel_requested` и `message`.

### CRITICAL-02 — `idle` ≠ свободный стол
- Единое правило `domain/print/bedOccupancy.ts` (`resolveBedOccupancy`):
  `CLEAR` только по записанной очистке; ничего не отслеживается → `UNKNOWN`;
  наблюдаемая печать важнее записи `CLEAR`.
- `bedCycles.latestByPrinter()` (по порядку вставки, не по `created_at`);
  `findOpenByPrinter` определён через текущий цикл.
- Применено везде: допуск (`evidence.ts`), прогноз освобождения
  (`release.ts`), последний рубеж dispatch (`reserve`: нет цикла / видимая
  печать → отказ), карточка принтера (`createRuntime.bedCycleFor`).
- **Внешние печати**: печать без канонического run открывает «внешний» цикл
  `RUNNING`; её окончание → `AWAITING_CLEARANCE` + операция снятия; при первом
  наблюдении после перерыва (рестарт, офлайн) завершённое задание, которое
  Albedo не может объяснить, тоже ставит стол в `AWAITING_CLEARANCE`.
  Подтверждение очистки запоминает задание, которое устройство показывало
  (`deviceLastJob`), чтобы не спрашивать повторно.
- Нельзя подтвердить очистку стола, пока принтер видимо печатает.
- Ограничение: Creality WS сообщает состояние числом без признака
  «завершено» — для него внешние печати фиксируются только по наблюдаемой
  печати (непрерывное наблюдение), а не задним числом.

### CRITICAL-03 — выбор лотка AMS Bambu
- `domain/printers/feedPlan.ts` — план подачи по филаментам задания: точное
  совпадение типа, затем цвет, затем активный лоток (только для однофиламентных
  заданий); иначе `AMS_SLOT_AMBIGUOUS` с вариантами выбора. Явный выбор
  оператора допускается только в пределах того же семейства материала. Два
  филамента в один лоток — только явным выбором.
- Новые неснимаемые причины: `AMS_MATERIAL_MISMATCH`, `AMS_SLOT_AMBIGUOUS`,
  `AMS_MATERIAL_UNKNOWN`, `AMS_STATE_UNKNOWN`, `AMS_FEED_UNSUPPORTED`.
- План вычисляется той же политикой допуска, **закрепляется в run**
  (`metadata.feed`) при резервировании и **перепроверяется по свежему отчёту
  перед публикацией**; подмена катушки → отказ, команда не отправляется.
- Формат `ams_mapping` приведён к вендорскому клиенту (Bambu Studio): массив по
  филаментам задания, значение — глобальный id лотка `ams_id×4+slot`, плюс
  `ams_mapping2`. Прежний 5-элементный «правый» массив сопоставлял
  однофиламентному заданию пятый филамент.
- Выбор лотка: `feedChoice` в `POST /api/print/launch/:taskId` и
  `?feed=0:3` в предпросмотре; кандидаты возвращают `feed`.
- **Не проверено на железе**: ферма сейчас сообщает A1 Combo без AMS (печать с
  внешней катушки, `use_ams:false`, как и раньше). Путь с AMS проверен только
  тестами; первый реальный запуск через AMS стоит провести под наблюдением.

### HIGH-17 — HTTP-принятие ≠ старт
- Фазы: `accepted` (устройство приняло команду; run `PENDING`, стол
  `RESERVED`, guard сохраняется) и `started` (печать увидена телеметрией или
  подтверждена устройством, как у Bambu). Общий каскад
  `confirmRunStarted` для dispatch и наблюдения.
- Принятая команда, после которой принтер 3 минуты не печатает → run `UNKNOWN`
  (принтер удержан, повтор не отправляется).
- Стартовый guard больше не снимается сразу после dispatch
  (`startNext`/`startNight`/`startPrinterFile`) — иначе рестарт в окне
  «принято, но не увидено» счёл бы команду неотправленной.
- `DispatchResult.phase`, окно запуска пишет «Команда принята принтером» вместо
  «Печать запущена».

Проблема: promotion переносит `task.artifactId` на G-code, и повторная нарезка

### HIGH-10 — утверждённая ревизия профиля неизменна
Проблема: ревизия была «байтами» (уникальный `raw_sha256`), а разрешённые
настройки (`resolvedJson`) пересчитывались **на месте** при каждом импорте.
Правка родительского пресета (или другой vendor-набор) молча меняла настройки
под id, на котором утверждён набор; набор оставался утверждённым.
- Миграция **017** (`017_profile_resolution_identity`): уникальность по паре
  `(raw_sha256, IFNULL(resolved_sha256,''))`; данные не переписываются.
- Импорт (`presetImportService.upsert`): разрешение, однажды полученное, не
  меняется. Те же байты с другим разрешением → **новая ревизия**; прежние
  помечаются `metadata.supersededBy` + предупреждение `profile_superseded`,
  их статус, настройки и происхождение не трогаются. Неразрешимость (пропал
  родитель) меняет только вердикт (карантин), записанные настройки сохраняются.
  Возврат прежнего разрешения делает прежнюю ревизию снова текущей (без третьей).
- Утверждённый набор на заменённой ревизии **остаётся утверждённым и режет
  ровно утверждёнными настройками** (проверено по JSON, переданному в Orca), но
  показывает предупреждение. Новый набор на заменённой ревизии создать нельзя;

  не предлагаются в форме нового набора.
- Счётчики и покрытие профилей считают байты один раз (без заменённых).

### HIGH-11 — нарезанный 3MF: реальный G-code, нормализованный принтер, выбранный payload
Проблема: `.gcode.3mf` оценивался по `slice_info.config`; вложенный G-code не

принтер писался в `data.targetPrinter`, а допуск читает `data.printerModel` —
проверка «файл собран для другого принтера» для пакетов **не срабатывала
никогда**; к тому же `slice_info` даёт внутренний код Bambu (`N2S`), не модель.

экспортировал пластину 2 (`plate_2.gcode`).
- `SafeZip.stream()` — потоковое чтение записи с теми же лимитами (счёт байт
  на лету, обрыв на лимите); G-code-анализатор принимает поток текста
  (`analyzeGcodeText`), один и тот же разбор для файла и записи архива.

  пластину → блокер `threemf_payload_ambiguous`); MD5-сверка с `.md5`

## Этап 3 — очередь и планировщик

Общее правило — `domain/print/assignmentAuthority.ts` (`assignmentHolds`): одна
таблица назначений хранит три разных вещи, и спрашивать «занято ли?» нужно
по-разному:
- **рекомендация** — `PROPOSED` в черновике плана: ничего не удерживает;
- **решение** — ручное размещение или размещение в подтверждённом плане:
  удерживает задание и принтер, пока не инвалидировано;
- **физическое удержание** — `RESERVED`/`ACTIVE`: удерживает всегда.

### HIGH-12 — черновые PROPOSED не блокируют ручную печать
Было: ручной запуск на принтере, который «предложил» черновик, переиспользовал
это предложение, и dispatch отказывал «подтвердите план перед запуском»;
предложение черновика для другого задания делало принтер «занятым» и для
`assignTask`, и для резервирования в dispatch.
- `launchService.liveAssignment`, `assignTask` (задание и принтер),
  резервирование dispatch (`listHoldingByPrinter`, вместо
  `findOpenByPrinter` с LIMIT 1, где собственное назначение могло заслонить
  чужое), поиск назначения для записи файла на устройстве — все по
  `assignmentHolds`.
- Ручное размещение снимает (инвалидирует) предложения черновика для этого
  задания; черновик со снятыми предложениями не подтверждается («пересчитайте»).
- Пересчёт плана считает ручное размещение решением: задание не предлагается
  заново (иначе подтверждение дало бы ему второе размещение), принтер занят.

### HIGH-13 — инвалидированные назначения не удерживают оборудование
Было: инвалидирование оставляло состояние `PROPOSED`, и такое назначение
продолжало делать задание «уже назначенным», а принтер «занятым». В том числе
ломался сценарий «оператор выбрал другой принтер» в окне запуска
(`ensureAssignment` инвалидировал старое назначение, а `assignTask` тут же
отказывал из-за него же).

### HIGH-14 — пересчёт не отменяет ближайшие подтверждённые задания
Было: черновик-пересчёт исключал «замороженные» (ближайшие) назначения из
пула, а при его подтверждении `cancelActive` отменял их вместе со старым
планом — ближайшие подтверждённые задания выпадали из всех планов.
- Подтверждение переносит замороженные назначения в новый план (`planId`,
  аудит `carried_over`, привязка сохраняется как подтверждённая); старый план
  отменяет только перепланированный «хвост».
- Если замороженное назначение сняли между пересчётом и подтверждением —
  отказ «пересчитайте черновик».

### HIGH-15 — снятие детали и подготовка стола в расписании
Было: следующая печать на принтере планировалась ровно на момент окончания
предыдущей (`freeAtMs = end`).
- Планировщик (`PlannerConfig.readyAfterPrint`): следующий старт не раньше
  «конец печати → ближайшее окно оператора → снятие детали (5 мин) +
  подготовка стола». Без известного окна оператора принтер в этом плане больше
  ничего не получает (`PRINTER_RELEASE_UNKNOWN`, «деталь снять некому») — та же
  честность, что у проекции освобождения для уже занятого стола. То же правило
  для «замороженных» печатей и для оценки «стол освободится» в пояснении.
- Новая настройка `SCHEDULER_BED_PREP_MINUTES` (по умолчанию 5), задокументирована
  в `.env.example`.
- Ограничение: смена материала/сопла перед печатью по-прежнему только
  предупреждение, во времени старта не учитывается.

### HIGH-16 — повтор FAILED возвращает задание в очередь
Было: после печати (любой исход) запись очереди `RELEASED` (терминальна), и
`releaseTask` для FAILED делал задание `QUEUED`, оставляя запись `RELEASED` —
«в очереди», но ни в одной очереди: невидимо планировщику и окну запуска.
- FSM записи очереди: `RELEASED → WAITING` (только для повтора; у задания одна
  запись — `task_id UNIQUE`). Повтор переоткрывает запись в конец очереди,
  аудит `retried`; прежний run остаётся FAILED в истории.
- UI повтора нет (только `POST /api/print/tasks/:id/release`) — этап 5.

## Этап 5 — история, повтор печати, пакетная подготовка ✅

Главное правило — `domain/print/reprint.ts`: завершённая печать — это история.
**Повтор — новая печать тех же проверенных байт**, никогда не переоткрытие и
не правка закрытого задания. Закрытое задание получает только строку аудита
`reprinted` с id новой печати.

### Повтор готового задания / повторное использование проверенного G-code
- `evaluateReprint` (чистая функция, общая для экрана истории и команды):
  печать завершена (COMPLETED/FAILED/CANCELLED) → файл есть (строка и байты
  в хранилище) → у файла есть хэш (не «имя на принтере») → не закрыта до
  нарезки → анализ актуальной версии → анализ допускает файл. Отказ — со
  стабильным кодом (`file_deleted`, `analysis_outdated`, …) и текстом
  «что делать».
- Два маршрута:
  - `variant` — печать из нашего слайсера, вариант на месте: новая печать
    получает **свою копию варианта** (тот же выходной артефакт, тот же
    закреплённый масштаб HIGH-07, тот же набор профилей и цель) и проходит
    обычный promote — пин принтера, проверки масштаба и профилей идут с ней;
  - `executable` — загруженный G-code / нарезанный 3MF, или слайс, чей вариант
    ушёл вместе с удалённой моделью: файл ставится в очередь как загрузка.
- Ни один маршрут не режет заново (`sliceCount` в тестах не меняется).
- Новая печать наследует только то, что относится к **работе** (название,
  материал, приоритет); окно времени, дедлайн, пин и разрешение «без
  оператора» спрашиваются заново — это решения об одной печати.
- Идемпотентность: `requestId` в теле; повтор с тем же ключом возвращает уже
  созданную печать (`deduplicated: true`), второй печати нет. Поиск — по
  аудиту закрытого задания, без новой колонки. Дашборд хранит неотвеченный
  ключ до ответа сервера, так что клик после потерянного ответа не плодит
  дубль.
- Всё в одной транзакции: отказ где угодно не оставляет ни черновика, ни
  копии варианта.
- `POST /api/print/tasks/:id/reprint`, `POST /api/print/slicing/variants/:id/reprint`
  (новая печать по готовому варианту, чьё задание закрыто или собрано из
  другого слайса; вариант, который его черновик ещё может принять, → отказ
  `promote_instead`).
- FAILED по-прежнему можно повторить тем же заданием (`/release`, HIGH-16) —
  в истории это кнопка «Повторить».

### История печатей и сохранённые настройки
- `GET /api/print/history?limit&cursor&state&printer`, `GET /api/print/history/:id`.
  «Печать» — завершённое задание, которое было в очереди или на принтере
  (черновик загрузки, отменённый вместе с файлом, — не печать).
  Keyset-курсор `updatedAt~id`, новые сверху (`tasks.listFinished`).
- Запись: последний run (принтер по имени, исход, длительность, филамент),
  файл, модель, **рецепт — как он был при нарезке**: набор, три закреплённые
  ревизии (машина/процесс/филамент), цель, масштаб, версия OrcaSlicer, оценки;
  `profileSetUsable` — можно ли выбрать этот рецепт сейчас. Линия: `reprintOf`,
  `previousTaskId`, `reprintedAs`.
- `actions` с сервера: `reprint` (разрешён/код/причина/маршрут), `retry`,
  `reprepare` (модель + принтер + рецепт для мастера).
- Сервис: `app/printQueue/history.ts` (`PrintHistory`), в рантайме — `history`.

### Повторная подготовка исходного файла
- «Подготовить заново» из истории открывает мастер «Новая печать» с моделью,
  принтером и рецептом той печати (`startNewPrintFrom`); `previousTaskId`
  уходит в `POST /slicing/slice` и пишется в линию нового черновика (только если
  это действительно печать той же модели). Тот же рецепт → тот же ключ кэша →
  готовый G-code сразу, без OrcaSlicer.
- В мастере: «Как в прошлый раз: «принтер» · «рецепт»» — принтер и рецепт
  последней готовой нарезки этой модели, если оба можно выбрать сейчас.

### Пакетная подготовка моделей
- `SliceService.createBatch` / `POST /api/print/slicing/batches`: до 25 моделей,
  один рецепт, одна цель. Каждая модель — обычный `createSlice` (те же
  проверки, кэш, одна подготовка на модель). Рецепт проверяется один раз
  (неизвестный/неутверждённый — отказ всего запроса); модель, которую нарезать
  нельзя, — своя строка с кодом и причиной. `metadata.batchId` на вариантах,
  аудит `slice_batch/requested`.
- `POST /api/print/slicing/batches/promote` (`promoteSliceVariants`): каждый
  вариант — своя транзакция, отказ одного не откатывает другие.
- Мастер: режим «Подготовить пакетом» — модели флажками (загрузка нескольких
  файлов), общее подтверждение единиц для STL, принтер, рецепт, «Нарезать все»,
  строка на модель, «Поставить готовые в очередь (N)», затем «Запустить» у
  каждой печати отдельно (у каждой свой стол).

### Интерфейс
- Новый рабочий раздел **«История»** (`features/history/{model,view,controller}.js`):
  фильтр по исходу, карточки (где, когда, сколько, материал, линия повторов),
  «Подробнее» — настройки; главная кнопка по ответу сервера: «Напечатать ещё
  раз» → окно запуска новой печати на прежнем принтере; FAILED — «Повторить»;
  без файла — «Подготовить заново».

## Этап 6 — безопасная автоматическая очередь (выключена по умолчанию) ✅

### Принцип: не второй путь запуска, а третий режим одной политики
- `DispatchMode = "manual" | "night" | "auto"` (`domain/dispatch/eligibility.ts`),
  `isUnattendedMode()` — «за стартом никто не стоит» (night, auto). Режим `auto`
  **не слабее ночного**:
  - **любой** `review` preflight — отказ (ночью — только список AT_NIGHT);
  - всё, что ночью отказ, — отказ и здесь: файл с хэшем и готовым анализом,
    G-code, объявленный целевой принтер, идентичность «имя+размер», без
    ручного переноса файла (Creality WS никогда не запускается автоматически),
    «принтер занят» — отказ;
  - принятый оператором `review`-вердикт **не считается** (принят не для этого
    старта; раньше условие было `mode !== "night"` — для `auto` оно бы сработало);
  - обязательное разрешение задания `unattendedAllowed` («можно печатать без
    присутствия оператора»);
  - предпочтение времени вместо ночного флага: `night` — только в ночном окне и
    если помещается (та же арифметика, `pushNightWindow`), `day` — только при
    операторе на смене (новая причина `AUTO_DAY_ONLY`; неизвестное расписание
    = оператора нет), `any` — в любое время.
- `LaunchService.launch(…, { mode: "auto" })` / `preview(…, { mode: "auto" })`:
  тот же путь (preflight → назначение → доставка → финальный гейт dispatch),
  но подтверждения и override **не принимаются** (ValidationError), а
  «подтверждаемые» блокеры (стол не отмечен, материал не сообщается) **остаются
  блокерами** — никто не ставит галочку за человека, цикл стола не пишется.
- `DispatchService.verifyOnDeviceFile` в `auto` строг как ночью.

### Исполнитель — `app/automation/autoQueue.ts` (`AutoQueueExecutor`)
- **Выключен дважды**: переключатель развёртывания `AUTO_QUEUE_ENABLED`
  (по умолчанию `false`; без него таймер даже не запускается) **и** правило
  оператора «Автоочередь» (`auto-queue`, по умолчанию выкл, хранится в
  state.json). Пока выключен переключатель, правило **заблокировано**: включить
  нельзя (409 `AUTOMATION_LOCKED`), а сохранённое ранее «вкл» считается «выкл».
- Проход: задания очереди `WAITING/QUEUED` по порядку, только с
  `unattendedAllowed`; размещённое человеком (ручное назначение или
  подтверждённый план) — только на тот принтер, никакого перепланирования;
  кандидат — по `preview(mode: "auto")`; старт — `launch(mode: "auto",
  actor: "auto-queue", idempotencyKey: auto:<task>:v<version>)`.
- **Защита от двойной отправки**: один проход за раз; проходы в одной очереди
  с start-next и ночным стартом (цепочка перенесена в рантайм —
  `FarmRuntime.runQueueDispatch`, общая для всех); не больше
  `AUTO_QUEUE_MAX_STARTS_PER_TICK` (1) стартов за проход и никогда два на один
  принтер; ключ идемпотентности на версию задания; ниже — уникальные индексы
  «один активный run на принтер и на задание» и стартовый guard.
- **Аварийная остановка**: если после ошибки у задания остался активный run
  (команда могла уйти) — правило выключается само (с причиной в ленте,
  сохраняется — рестарт не включит обратно), принтер удержан до решения
  человека. Так же — если автоматический запуск, принятый принтером, так и не
  подтвердился (run `UNKNOWN` с `mode: auto`).
- Чистый отказ (до отправки или однозначный отказ устройства) — задание
  отдыхает `AUTO_QUEUE_RETRY_COOLDOWN_MS` (15 мин), если не изменилось.
- **Восстановление**: в памяти нет ничего, что нельзя потерять; первый проход
  через `AUTO_QUEUE_STARTUP_DELAY_MS` (2 мин) после старта — когда recovery
  отработал и телеметрия свежая. Запуск — последним в `FarmLifecycle.start`,
  остановка — первой в `stop()` (ждёт проход в полёте).
- **Dry-run** (`plan()`): что запустилось бы сейчас и почему нет — без
  побочных эффектов, работает и при выключенной автоочереди.
- API: `GET /api/automations/auto-queue` (статус + dry-run),
  `POST /api/automations/auto-queue/tick` (409, если не разрешена или не
  включена), включение — прежним `POST /api/automations/auto-queue/toggle`.
- Настройки (`.env.example`, раздел планировщика): `AUTO_QUEUE_ENABLED=false`,
  `AUTO_QUEUE_INTERVAL_MS=60000` (мин. 10 с), `AUTO_QUEUE_STARTUP_DELAY_MS=120000`,
  `AUTO_QUEUE_MAX_STARTS_PER_TICK=1` (макс. 5), `AUTO_QUEUE_RETRY_COOLDOWN_MS=900000`.

### Найденный и исправленный попутно изъян (не только автоочередь)
- `DispatchService.reserve` пишет в задание подсказку `targetPrinter = A`,
  откат однозначного отказа её не снимал, а ручное размещение на B подсказку
  не обновляло — dispatch отказывал «расхождение назначения». Тот же сценарий
  ломал «Повторить» после FAILED на другом принтере и ручной перезапуск на
  другом принтере после отказа устройства. Теперь ручное размещение
  (`assignTask` без плана) переносит мягкую подсказку на выбранный принтер;
  жёсткое закрепление (`pinnedPrinterId`) и размещения плана не трогаются.
- **Снятое ручное размещение продолжало быть «резервом»** (остаток HIGH-13):
  `EligibilityQueries.confirmedReservation` брал **самое старое** назначение,
  и снятое (инвалидированное) ручное размещение отказывало задание на всех
  принтерах («назначение устарело», «расходится с планом») — даже после того,
  как человек разместил его заново. Теперь решает **самое новое** действующее
  решение; снятое ручное размещение не связывает ничего; снятое размещение
  подтверждённого плана по-прежнему требует перепланирования, если нового
  решения нет. Прямой запуск снятого назначения по-прежнему отказывается
  (`assertExecutable`).

### Уточнения исполнителя (после первого полного прогона этапа)
- Аварийная остановка — только когда активный run принадлежит **этой**
  попытке (её ключ идемпотентности или `mode: auto`); чужой ручной запуск того
  же задания, успевший раньше, — «ждёт», не авария.
- Остановка из-за неподтверждённого авто-старта — только для run, который
  **ни разу не был замечен печатающим** (`startedAt === null`); потеря
  телеметрии посреди начатой печати держит лишь свой принтер.
- Исполнитель убирает за собой: размещение, сделанное его попыткой, которая
  не стартовала (доставка не подтвердилась, рестарт посреди попытки),
  снимается — оно не решение человека и не привязывает задание к принтеру.
- Dry-run показывает паузу после отказа (`AUTO_COOLDOWN`).

### Интерфейс

### План развёртывания (выполнять только с разрешения владельца)

Что меняется: оба образа (dashboard, orchestrator), конфигурация контейнера
оркестратора (новые переменные в `compose.yml`), миграция **017** (только
индексы `profile_revisions`, данные не переписываются). Автоочередь остаётся
выключенной.

**Требует остановки сервисов:** пересоздание оркестратора (смена образа и
конфигурации; миграция при старте; простой ~30–90 с — старт, smoke-нарезка
Orca, первый опрос) и любое восстановление БД в прод. Пересоздание dashboard
печать не затрагивает.

**Нельзя при активной печати:** пересоздавать или перезапускать оркестратор
(`deploy.sh` сам удержит его — не использовать `--allow-active-prints`),
восстанавливать БД, вручную делать `docker compose up -d` / `restart`,
откатывать образ.

1. **Состояние фермы (go/no-go).**
   `curl -s 'http://127.0.0.1:8090/api/print-orchestrator/restart-safety?window=600'`
   → `activePrints: 0`, `safeToRestart: true`; `…/ready` → `ready: true`;
   `df -h /` ≥ 4 ГБ свободно; `grep AUTO_QUEUE .env` — пусто (или `false`);
   `git log -1`, `git status` — ревизия с финальными правками. Посмотреть
   глазами на столы всех трёх принтеров.
   **Ни один принтер не печатает**, в том числе то, что запущено вне Albedo
   (`untracked-print` в `restart-safety`): релиз меняет API, а при занятой
   ферме `deploy.sh` применит только dashboard (`DEPLOY PARTIAL` — новый
   интерфейс против старого API). На время деплоя (~5 мин) печать не
   запускать. `./scripts/deploy.sh preflight` — без предупреждения о печатях.
2. **Резервная копия.** `./ops/backup/backup.sh --full`, затем
   `./ops/backup/verify.sh` (новейший полный набор) — должен пройти. Это

   `docker logs atelier-print-orchestrator 2>&1 | grep -E "migrations applied|017|slicing runtime available|catalog imported"`

   `…/api/print/slicing/runtime` → `active: 19, quarantined: 0, missingParents: []`;

   карточке. KE: проверить стол → «Стол пуст — подтвердить». A1: стол записан

   снятия детали», KE — «Стол не подтверждён»: снять детали, подтвердить.

   файла; A1 — Bambu, внешняя катушка); «Остановить» на тестовой печати → стол

   наблюдением.
9. **Критерии успеха.** `DEPLOY SUCCESS`; схема 17; оба контейнера healthy;

10. **Если что-то пошло не так.**
    - До подмены (сборка, место, gate): прод не тронут — разобраться, повторить.
    - Новый оркестратор не стал healthy / проверки не прошли:
      `docker compose logs --tail 200 print-orchestrator`. **Откат одним образом
      невозможен** — после 017 старый образ не стартует (`SchemaTooNewError`,
      проверено). Путь: `docker compose stop print-orchestrator` →
      `./ops/backup/restore.sh --set <набор из шага 2> --to-production --i-mean-it`
      → `./scripts/deploy.sh rollback`. Теряется только то, что записано после
      деплоя.
    - Только для эксперта и только при остановленном оркестраторе, после
      бэкапа: 017 меняет лишь индексы, поэтому её можно снять SQL-ом, если
      `SELECT raw_sha256 FROM profile_revisions GROUP BY 1 HAVING COUNT(*) > 1`
      пуст: `DROP INDEX idx_profile_revisions_content; DROP INDEX idx_profile_revisions_raw_sha; CREATE UNIQUE INDEX idx_profile_revisions_raw_sha ON profile_revisions (raw_sha256); DELETE FROM schema_migrations WHERE version = 17;`
      — затем `./scripts/deploy.sh rollback` (проверено на копии рабочей БД:
      после этого SQL текущий рабочий образ стартует штатно).
    - Неопределённый запуск на железе: не повторять; проверить принтер и
      отметить исход в окне запуска («отметьте, что произошло»).
11. **Автоочередь — отдельным решением, после приёмки.** `AUTO_QUEUE_ENABLED=true`
    в `.env` → `./scripts/deploy.sh` (пересоздание оркестратора по конфигурации,
    под тем же gate) → «Автоматизации»: проверить dry-run, включить правило;

    наблюдением. Ограничение: K2/KE в простое не сообщают материал — их

### Откат после успешного деплоя

`deploy.sh rollback` теперь возвращает к **новым** образам (они —
`last-known-good`). Возврат к `3db702e` — только при простаивающей ферме
(`restart-safety` → `safeToRestart: true`) и с решения владельца:

```bash
docker compose stop print-orchestrator print-dashboard
# теряется всё, записанное после 2026-10-16 06:02 UTC:
./ops/backup/restore.sh --set /home/miha/atelier-backups/sets/daily/2026-10-16T06-02-00Z --to-production --i-mean-it
docker tag atelier-print-orchestrator:rollback-3db702e atelier-print-orchestrator:latest
docker tag atelier-print-dashboard:rollback-3db702e atelier-print-dashboard:latest
docker compose up -d --no-build
```

Сохранить данные после деплоя можно экспертным путём Б (SQL-откат 017,
проверен на копиях): остановить оркестратор, бэкап, проверить отсутствие
дублей `raw_sha256`, SQL из плана, затем те же `docker tag` и `up`.
Теги `:rollback-3db702e` не трогает ни `deploy.sh`, ни его очистка —
снять их вручную, когда приёмка завершится.

### План приёмки на реальном оборудовании (после отдельного разрешения)

**Подготовка (оператор):** включить KE и A1 и дождаться свежей телеметрии на
карточках; физически освободить все три стола и подтвердить в Albedo (K2 —
«Снять модель и освободить стол», KE — «Стол пуст — подтвердить», A1 — по
показанному состоянию, глазами в любом случае); заправить PETG (все
утверждённые рецепты — PETG 0.4); у A1 — внешняя катушка, AMS не
используется. Порядок принтеров: **K2 → A1 → KE**. Модель: кубик 20 мм
(~15–30 мин) или пластина 20×20×5 мм (~10 мин). Оператор у принтера на
первом слое.

**Цикл для K2 и A1** (одинаковый):

| # | Шаг | Ожидается |
|---|---|---|
| 1 | «Новая печать» → загрузить STL → единицы «мм» | анализ «годится» |
| 2 | Принтер | карточка «готов» (после подтверждения стола) |
| 3 | Рецепт | K2: «K2 · PETG 0.4 · стандарт»; A1: «A1 · PETG 0.4 · 2.3.0» |
| 4 | Слайсинг | вариант готов за секунды, оценки времени и филамента |
| 5 | «Это и печатаем» | задание в очереди |
| 6 | Окно запуска | принтер, файл, сопло 0.4, PETG; K2 — подтвердить «Материал загружен» (Klipper в простое не сообщает); A1 — внешняя катушка, без AMS; «Запустить» один раз |
| 7 | Отправка и старт | файл на принтере (K2 — Moonraker, A1 — FTPS + MQTT); «Команда принята» → «Печать началась»; ровно одна команда старта |
| 8 | Печать | прогресс, ETA и температуры обновляются |
| 9 | Завершение | run `SUCCEEDED`, стол «Ждёт снятия детали» |
| 10 | Снять деталь → «Снять модель и освободить стол» | стол `CLEAR` |
| 11 | «История» | запись: рецепт, длительность, расход |
| 12 | «Напечатать ещё раз» | новое задание тех же байт без нарезки, без дубля (печатать — по желанию) |

**KE** (путь (а), пока не решён дефект 13): нарезать кубик как обычно → в
«Новой печати» загрузить G-code → анализ `review` (`BED_MESH_CALIBRATE`) →
подтвердить проверку → окно запуска: подтвердить «Стол пуст» и «Материал
загружен» → Albedo попросит перенести файл вручную (у Creality WS нет загрузки
и удалённого старта) → перенести на KE, подтвердить перенос (именное
подтверждение) → запустить печать на экране KE → Albedo должен увидеть печать
по телеметрии и привязать её к заданию → завершение → «История».

**Дополнительно, после базового цикла на всех трёх:** «Остановить» на второй
короткой печати K2 после первого слоя (run остановлен, стол «Ждёт снятия
детали», лишних команд нет); двойной клик «Запустить» — один старт; пакет из
2–3 маленьких моделей; AMS и `plate_2` на A1 — позже, отдельными запусками под
наблюдением.

**Правила остановки:** исход запуска «не подтверждён» — не повторять, проверить
принтер и отметить исход в окне запуска; что-либо неожиданное у принтера —
остановить на самом принтере, затем разбираться. Автосписание филамента в
fulfillment сработает по завершении (на K2 остаток PETG black мал — будет
«долг», это не ошибка приёмки).

**Критерии приёмки принтера:** ровно одна команда старта; run `RUNNING` →
`SUCCEEDED`; стол «Ждёт снятия детали» → `CLEAR` после подтверждения;
полная запись в «Истории»; повтор создаёт новое задание тех же байт.
