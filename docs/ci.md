# CI и сопровождение runner

[GitHub Actions](https://github.com/4245877/Albedo-Atelier/actions) выполняет проверки при PR, push в `main` и ручном запуске `CI`. Ручной запуск доступен после попадания workflow в ветку по умолчанию. Прогоны одной ветки или PR отменяют свой устаревший прогон того же типа. Новый SHA проверяется в отдельной среде GitHub-hosted Ubuntu 24.04.

| Job | Проверка |
| --- | --- |
| `secret-scan` | Маркеры приватных ключей в отслеживаемых файлах. Журнал показывает пути без содержимого. |
| `print-orchestrator` | Установка по lockfile, typecheck, unit и integration, отчёт о сложности, `pnpm audit --prod --audit-level moderate`. |
| `print-dashboard` | Node-тесты, обязательный Chrome CDP против mock API, сборка образа, запуск `nginx -t` через entrypoint образа и Trivy. |
| `deploy-script` | Синтаксис shell, ShellCheck, обе конфигурации Compose с тестовыми значениями, сценарии выкладки и отката с fake Docker. |
| `orchestrator-image` | Сборка `production` и `production-orca` с общими кэшированными слоями, `/ready` без сети и со свежими данными, Trivy на обоих образах. |

Workflow использует `contents: read` и checkout без сохранения Git-учётных данных. Node и Chrome закреплены по версии, действий GitHub — по SHA коммита. pnpm берёт версию из `apps/print-orchestrator/package.json`. Кэшируется только pnpm store с ключом от lockfile. Установка всегда использует `--frozen-lockfile`. Компиляция приложения в CI выполняется в Dockerfile. Оба target используют результат общей стадии сборки.

Trivy скачивается из [официального релиза](https://github.com/aquasecurity/trivy/releases) и проверяется по SHA-256. При смене сканера обновите версию и контрольную сумму вместе. Для Chrome используйте [официальный дистрибутив Chrome for Testing](https://googlechromelabs.github.io/chrome-for-testing/) и обновляйте его SHA-256 вместе с версией. База Trivy обновляется на каждом runner. Gate блокирует исправимые HIGH и CRITICAL в образах и срабатывает на найденные секреты этих уровней. Артефакты `dashboard-image-scan` и `orchestrator-image-scans` хранятся 14 дней и содержат версии пакетов, результаты скана и число срабатываний на секреты без совпавших значений или переменных среды образа. Образы собираются для валидации на runner. Выкладка выполняется отдельно с сервера по [инструкции сопровождения](operations.md).

## Разбор и повторный запуск

1. Откройте job и первый неуспешный шаг. В `Set up job` проверьте доступность SHA каждого action и образ runner. У Aqua старые теги Trivy Action без префикса `v` удалены после [инцидента с цепочкой поставки](https://github.com/aquasecurity/trivy/discussions/10462).
2. При сбое pnpm сопоставьте найденный GHSA с версией в lockfile. Перегенерируйте lockfile версией pnpm из манифеста и проверьте тесты и `pnpm audit` по [инструкции тестирования](testing.md#оркестратор). Ограничения override относятся к зависимостям конкретных родителей. При их удалении снова проверьте версии реально возникающих путей в lockfile.
3. При сбое Trivy откройте JSON артефакт соответствующего job. Если отчёта нет, проверьте скачивание инструмента, доступность базы и состояние Docker по журналу. Если есть исправленная версия пакета, обновите пакет или базовый образ, повторите скан и проверьте оба варианта Compose. SHA образов закреплены в Dockerfile. Системные зависимости `apt` при новой сборке берутся из репозиториев Debian, а оценки уязвимостей — из текущих баз.
4. После исправления проверяйте новый SHA. Если подозреваете временный сбой сети или хостинга, повторите job на том же SHA через **Re-run failed jobs**. Для повторной полной проверки используйте **Run workflow**. Сверьте прохождение обязательных шагов, счётчики тестов и наличие обоих артефактов.

## Локальные вычисления

`think-centre` обслуживает production Docker, PostgreSQL соседнего проекта, камеры и очередь печати. На момент проверки у него 2 логических CPU, 7,2 ГиБ RAM и около 29 ГиБ доступно в корневой файловой системе. Аппаратная виртуализация недоступна в текущей конфигурации. Ресурсы временной файловой системы `/tmp` ограничены оперативной памятью. Доверенные локальные тесты можно запускать по одному комплекту в отдельном checkout в пользовательском cgroup. Сборка образов, браузер и публичные PR остаются в GitHub Actions. [Рекомендации GitHub по защите self-hosted runners](https://docs.github.com/en/actions/reference/security/secure-use).

Для переноса вычислений используйте отдельный локальный сервер с аппаратной виртуализацией и сетевой изоляцией. Начните с одного эфемерного VM runner на один job, 2 vCPU, 4 ГиБ RAM и дискового лимита 20 ГиБ. Пересмотрите лимиты по пиковым показателям production-orca и браузера. Для первой миграции подойдут доверенные тесты оркестратора на проверенном SHA. Следом можно перенести сборки и сканы с Docker внутри VM.

- Зарегистрируйте runner в закрытом репозитории команды. Ограничьте группу runner выбранным workflow на защищённой ветке. Доверенный запуск проверяет, что SHA относится к канонической ветке публичного репозитория. Публичные PR продолжают проходить обязательные проверки на GitHub-hosted VM.
- Выделите VM отдельный сегмент с исходящим доступом к GitHub, реестрам и базам сканера. Блокируйте маршруты к production, LAN принтеров и Tailscale на границе сегмента. Docker, рабочие файлы и временные credentials принадлежат VM. Хостовые bind-mounts и сокеты исключены.
- Подготавливайте VM из проверенного образа и регистрируйте её как эфемерную. После завершения или аварии выгружайте диагностические логи в доверенное хранилище и удаляйте рабочий диск этой VM. Контроллер восстанавливает доступность созданием новой VM. Обновляйте закреплённый образ и runner до истечения 30-дневного окна поддержки GitHub при отключённых автообновлениях. [Документация GitHub по эфемерным runners](https://docs.github.com/en/actions/reference/runners/self-hosted-runners).
- До переключения сравните два прогона одного SHA, проверьте изоляцию, квоты, удаление тестовой VM после принудительного сбоя и восстановление очереди. При проблемах остановите выдачу новых VM и оставьте проверки на GitHub-hosted.
